# 0.16.3 → 0.18.3 + Studio：只记一个入口

**本轮只准备软件、测试和交付包，板端仍未执行。** 新包为 `microduck-install-kit-0.6.0.tar.gz`，包含冻结的0.5.0机器人升级器、固定官方/native程序、Studio源码、浏览器/模型资产和离线依赖。一次上传、解压后，进入 `microduck-install-kit-0.6.0`：

```sh
sudo ./duck.sh
```

**按 `N`，只完成当前一步；看清新状态，再按下一次 `N`。** 不需要填写资产路径，不需要自己选择底层脚本；遇到未知、正在执行或中断状态，入口会停下来说明原因。

## 简明升级方案

1. **先有完整退路。** 在独立Linux救援系统启动，原盘未挂载，使用同一入口的 `I → 1` 制作原盘镜像；脚本询问盘/外部镜像路径，核验身份、完整SHA与逐字节比较。完成后回到原0.16.3系统。不能把在线应用备份当整盘备份。
2. **进入安装套件，运行 `sudo ./duck.sh`，按 `N`。** 第一次先检查程序/运行库/ONNX及原校正，再询问已制作镜像的位置、停止服务并保存应用备份。失败就停，不继续安装。
3. **按状态提示继续 `N`：** 官方0.18.3 → 原校正与Tools → 明确启动。每步保留旧升级器的独立确认及恢复记录；不自动连续执行，不启用policy或运动。
4. **继续 `N` 安装Studio。** 输入一次板端固定局域网IPv4；包自动找到浏览器资产和10个离线wheel，先检查再安装。控制/Camera默认关闭。再次 `N` 只启动Studio和助手。
5. **按 `P` 生成一次性登录码。** 核对终端显示的CA指纹，通过可信通道将CA装到手机/电脑，再打开状态显示的HTTPS入口。先看真实反馈和原校正回执；现场验收完成后再明确调整所需开关。

这是“每次只完成一步”的向导，不是无人值守升级。执行前仍须按现场要求支撑机器人、断开舵机动力；启动robotd会打开总线。只知道IMU芯片面朝上不足以更改安装轴向；旧方向和比例保持原值，不猜16.4。

## 屏幕上的状态怎样理解

```text
Duck 安装助手 | 目标：robotd 0.18.3 + Studio 0.6.0
机器人：0.18.3 | 进程已启动，等待真实回执
校正：待真实运行回执核对
Studio：not_installed | 未启动/未知
下一步：安装独立Studio
为什么：离线安装只读界面；校正回执仍单独验收
```

上述是**合成示例**，不是板端结果。界面把四件事分开：文件版本、进程是否运行、真实校正回执、Studio状态。没有舵机/IMU时，不能把“已启动”当“实机验收通过”，也不会因为没有回执而不断重启robotd。可以完成监控界面准备，运动/性能仍待现场验收。

| 按键 | 做什么 | 对服务的影响 |
|---|---|---|
| N | 根据当前状态继续一步 | 显示意义后调用对应原引擎；不会越过失败 |
| S | 重新读取状态 | 不安装、不停服务 |
| P | 生成网页一次性登录码 | 不进行蓝牙配对，不写机器人配置 |
| C | 配置入口 | Studio开关保存后保持停止；原校正/相机维护另行选择并确认 |
| R | 恢复/回退 | 数字菜单说明范围，选定后才执行对应动作 |
| I | 整盘镜像 | 仅救援系统；备份读取原盘，恢复覆盖目标盘 |
| X | 停止Studio | 不换robotd版本、不自动恢复手柄 |
| Q | 退出向导 | 不撤销已经完成的步骤、不自动重启服务 |

C菜单的“仅监控”把Studio控制/Camera都关；保存开关会停止Studio，回主界面按N才重新启动。原IMU/关节维护会临时打开原维护Web；加载校正会重启robotd/Tools；相机应用可能重启mediad。调用这些原工具前，必须先停止Studio并明确处理手柄交接，不能并行改变控制服务。

## 只需几条可复制命令

下列命令均在**完整安装套件根目录**；不是Git源码目录。

```sh
sudo ./duck.sh                 # 打开向导，最推荐
sudo ./duck.sh status          # 只看当前状态、原因和下一步
sudo ./duck.sh next            # 只预览当前一步，不修改
sudo ./duck.sh next --apply    # 只执行当前一步，仍按提示确认
sudo ./duck.sh studio-stop     # 预览：只停止Studio的范围
```

首次Studio安装在终端输入IP，非交互执行可明确加 `--server-ip 实际IPv4 --confirm EXECUTE`；这不替代板端执行授权。自动路径只设置默认监控状态；已有Studio不会被重复安装或重置Web配置。遇到不同/损坏登记先审阅，不删除登记强行继续。

## 失败、断线、回退分别怎么做

**先重开同一 `sudo ./duck.sh`，按 S。**

| 显示/目的 | 选择 | 意义 |
|---|---|---|
| 原任务仍在执行 | 等待 | 不重复N，不杀更新器，不发第二次安装 |
| 机器人升级中断 | R → 1 | 原升级器核对真实事务/版本，不重新提交安装 |
| Studio安装/配置中断 | R → 2 | 撤销Studio未完成安装/配置，不恢复机器人镜像 |
| 手柄仍暂停 | R → 3 | 现场全部按键释放、摇杆归中后，明确交还；不删pending文件 |
| 卸下Studio | R → 4 | 移除其服务/配置和自有条件，保留版本文件；不降robotd |
| 回同版官方0.18.3 | R → 5 | 停止相关服务，换回官方robotd；不是回0.16.3 |
| 安装提交前取消维护 | R → 6 | 原0.16.3仍在且未提交安装时，恢复本次维护前状态 |
| 完整回原0.16.3 | I → 2 | 从救援系统核验镜像/原盘后覆盖整盘 |

手柄待交还、Studio仍运行、未完成事务、备份介质离线、实际版本/文件哈希未知时，下一步会阻断。向导不会自动交还手柄、修复配置、初始化、卸力或运动。

## 程序和运行库是否已准备好

- 官方0.18.3的13个程序、两个native校正程序复用冻结0.5.0交付；native已交叉编译，目标GLIBC2.30、最高符号需求2.29。新向导不重编或替换它们，机器人运行库/ONNX检查仍由原引擎执行。
- 入口优先使用系统已有的 `python3.11`，升级器和Studio共用该解释器。没有匹配的Python时先停止，不自动安装Python或先改机器人。
- Studio与向导为Python源码；浏览器/模型资产已准备，服务依赖为固定 **CPython3.11 Linux ARM64** wheels。预检核对系统/模块/工具、浏览器必需文件和所有wheel哈希；setup内真正建立venv并检查导入。Python其他ABI、32位或不匹配运行库不自动安装，也不宣称可运行。
- 向导不自动apt安装、不连接SSH、不下载latest，不改原升级器会话。已有0.5.0会话仍按同机器、同运行包指纹由冻结引擎核对；两个状态引擎保留各自文件和锁。
- Studio配置 `/etc/microduck-studio/config.json`；安装登记 `/var/lib/microduck-studio-install/`；机器人升级登记 `/var/lib/microduck-tools-manager/`；新向导只多一个互斥锁目录 `/var/lib/microduck-install-assistant/`，不另造升级完成标记。
